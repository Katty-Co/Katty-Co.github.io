# Working on this repository

Context for Claude Code (or any agent) picking this project up fresh.

## What this is

The website for **Katty &amp; Co.**, a pet sitting business in Vancouver, BC
(boarding, day care, drop-in visits, dog walking), owned by Alejandra. Maintained
by Miguel Monzones.

Deployed via **GitHub Pages** at the custom domain <https://kattyco.ca>. Because
the repo is named `Katty-Co.github.io`, it is the `Katty-Co` org's root Pages
site and publishes automatically from `main` — there is no Actions workflow and
no build step *on GitHub's side*. Push to `main` and it goes live within a minute
or two. `katty-co.github.io` 301-redirects to the custom domain.

### The custom domain, and the Cloudflare trap

`kattyco.ca` is registered at GoDaddy but uses **Cloudflare nameservers**
(`konnor`/`colette.ns.cloudflare.com`) for DNS. `CNAME` at the repo root holds
`kattyco.ca` and **must not be deleted** — it is what binds the domain to this
Pages site. It is explicitly whitelisted in `.gitignore`; without that entry the
`/*` whitelist silently refuses to re-add it if it ever leaves the index.

`ORIGIN` in `tools/build.js` is `https://kattyco.ca`, so canonical, `og:url` and
`sitemap.xml` all name the custom domain rather than the github.io host.

**If HTTPS breaks with Cloudflare error 525, this is why:** GitHub Pages issues
its own Let's Encrypt certificate for the custom domain, and it validates over
HTTP against the domain. If the Cloudflare records for `kattyco.ca` / `www` are
**proxied** (orange cloud), the validation request never reaches GitHub, so the
certificate is never issued. Cloudflare then tries HTTPS to an origin holding no
matching certificate and returns 525. It is a deadlock, not a transient error —
waiting does not fix it.

The cure is to set both records to **DNS only** (grey cloud) until GitHub reports
the certificate as issued and *Enforce HTTPS* becomes selectable. After that you
may re-enable the proxy with SSL/TLS mode **Full (strict)**; leaving it on DNS
only is also fine, since Pages already fronts the site with its own CDN.

Diagnosing it from the shell:

```bash
gh api repos/Katty-Co/Katty-Co.github.io/pages --jq '{cname,https_enforced}'
# https_enforced:false  => no certificate yet
curl -sI --resolve kattyco.ca:80:185.199.108.153 http://kattyco.ca/ | head -1
# 200 here proves the origin is fine and the problem is the certificate
```

Note the MX record points at purelymail, so email is live on this domain.
MX records are never proxied, so toggling the orange cloud cannot affect mail.

Note: the business is **Katty &amp; Co.**; **Kat** is the resident cat. Both spellings
are correct in their own context — do not "fix" one into the other.

## Read this before editing anything

### 1. The seven `index.html` files are generated. Do not hand-edit them.

They are compiled from the Claude Design canvas sources that live **outside this
repo**, in `Website Pages/` in the parent folder:

```
Website Pages/
  index.dc.html  services.dc.html  about.dc.html  pack.dc.html
  reviews.dc.html  faq.dc.html  booking.dc.html
  SiteHeader.dc.html  SiteFooter.dc.html  PawStrip.dc.html
  support.js   img/
```

Edit those in the canvas, then re-run the compiler (below). Any change you make
directly to a generated `index.html` will be silently destroyed on the next build.

`assets/site.js` is the exception — it is hand-written and is the right place to
change behaviour.

### 2. How the compile works, and why it is shaped this way

The `.dc.html` sources are **not** static HTML. They use `<x-dc>`, `<sc-if>`,
`<sc-for>`, `<dc-import>` and `{{ }}` bindings, and they depend on `support.js`,
a client-side runtime that pulls **React, ReactDOM and Babel from unpkg.com** and
compiles the templates in the browser on every page load.

Shipping that directly would mean a blank page until third-party JS arrives, no
SEO, and a hard dependency on a CDN staying up. So the build **runs the real
runtime once, locally, and freezes the result**:

1. **Serve** `Website Pages/` over HTTP (the runtime uses `fetch` for
   `<dc-import>`, so `file://` will not work).
2. **Open each page in a browser** and let the runtime render it.
3. **Capture** `document.documentElement.outerHTML` into `tools/captured/<page>.html`,
   stripping `support.js`, the unpkg script tags and the canvas-only styles.
4. **Post-process** with `node tools/build.js`, which rewrites links to clean
   URLs, injects the responsive header, wires the forms and writes the output.

Using the real runtime for step 2 is deliberate: it guarantees the static output
matches the canvas exactly, instead of re-implementing the template language.

**Step 2 needs a browser and is not scripted.** The captures in `tools/captured/`
are intermediates and are *not* committed, precisely so nobody rebuilds from
stale input. Regenerate them whenever the design changes.

Two capture traps, both already handled — do not regress them:

- **The hover rules live only in the CSSOM.** The runtime injects
  `.scp0:hover { … }` and friends via `insertRule` into a `<style>` tag whose
  `textContent` is empty. A naive `outerHTML` capture loses every hover state
  silently. The capture must serialise `[...sheet.cssRules]` back into the tag first.
- **The header state depends on the viewport at capture time.** `SiteHeader`
  used `matchMedia('(max-width: 880px)')`, so a capture freezes *either* the
  desktop nav *or* the hamburger, depending on window width — and a detached
  browser tab reports `innerWidth === 0`, which silently yields the mobile one.
  The build therefore **discards whatever header was captured** and injects a
  single responsive header built from `SiteHeader.dc.html`, switched by a CSS
  media query. That is strictly better than the original: no JS, no layout shift.

### 3. The build guards. Keep them passing.

The previous deployment of this site was a 9.2 MB single-file bundle in which the
entire interactive layer was dead — the export serialised handlers as
`sc-camel-on-click="{{ goPets }}"` and nothing ever compiled them, so every nav
link was inert and only the landing view rendered. `tools/build.js` ends with
guards so that class of failure cannot ship again. Each generated page is checked
for:

`{{ binding }}` · `sc-camel-on-*` · `<sc-if>` / `<sc-for>` · `<dc-import>` ·
`style-hover` / `style-active` · `unpkg.com` · `support.js` · `.dc.html` links ·
missing `lang` · missing `<meta name="description">`

The build also throws outright if a form field it expects is missing. **A build
that prints anything other than `guards: all pages clean` must not be pushed.**

### 4. The forms are real. Treat them as such.

Both the booking enquiry and the review form POST to **Formspree**
(`https://formspree.io/f/xjybqoar`), which emails Alejandra.

In the canvas source these forms are decorative — `submit` is
`e.preventDefault(); setState({ sent: true })`, with no `action` and no `name`
attributes, so a visitor got a cheerful confirmation and the enquiry went
nowhere. The build adds the `action`, the field names, a `_subject`, a `_gotcha`
honeypot, and the contact fields (name, email, phone) that the design never had.

Consequences to respect:

- The form works **without** JavaScript — `action` and `method` are real
  attributes, so a no-JS visitor gets Formspree's own thank-you page.
  `assets/site.js` upgrades that to an in-page confirmation via `fetch`.
- Fields inside a hidden pet block are **disabled** by `site.js` so they are not
  submitted. If you add a conditional block, disable it the same way.
- Formspree's free tier is **50 submissions/month across both forms**. If
  enquiries start getting dropped, that is the first thing to check.

### 5. Images go through a pipeline. Do not bypass it.

The build copies only images the pages actually reference, then for each JPEG,
**in this order**:

1. **Bakes in EXIF rotation.** Phone photos are stored unrotated with an
   orientation flag. Since step 3 deletes that flag, the rotation must become
   real pixels first — otherwise the picture ships sideways. This is not
   hypothetical: the Kat photo on `/about/` is orientation 6 and did exactly that.
2. **Downscales** anything over 900 KB to 1200 px (via `sips`). That same photo
   arrived as a 4032 × 3024, 3 MB camera original for a small square slot.
3. **Strips APP1 (EXIF/XMP), APP13 (IPTC) and COM.** These photos are taken in
   Alejandra's home and arrive carrying **GPS coordinates** — publishing them
   would put her home address in a file on a public website. APP0 (JFIF),
   APP2 (ICC colour profile) and APP14 (Adobe) are deliberately kept, because
   dropping those shifts the rendered colours.

So: drop new photos into the canvas source and rebuild. Do not hand-copy images
into `img/`, or they will skip all three steps.

The build **fails** (exit 1) if a page references an asset that does not exist.
A narrower earlier version of that check only looked at `img/`, and silently
shipped a broken image that the canvas had left at the source root — hence
`ASSET_RENAME` in `tools/build.js`, which gives such files a real home.

### 6. `.gitignore` is a whitelist. Keep it that way.

The working folder also holds roughly **2.6 GB of raw source photography and
video** — `Dogs/`, `Cats/`, `Photos-1-001/`, and a 1.3 GB zip. None of it belongs
in git; the zip alone exceeds GitHub's hard 100 MB per-file limit.

So `.gitignore` ignores everything (`/*`) and opts individual paths back in. When
adding a genuinely new tracked path, add a matching `!` entry. Do not replace
this with a conventional denylist.

Always confirm what you are about to commit:

```bash
git diff --cached --name-only
```

## Running it locally

Any static server will do — but use one that maps `/services/` to
`/services/index.html`, or the clean URLs will 404:

```bash
python3 -m http.server 8766
```

Then visit <http://localhost:8766>.

## Verifying a change

1. `node tools/build.js` prints `guards: all pages clean`.
2. Load the site and click through **all seven** nav links — the whole point of
   this rewrite is that they navigate.
3. Console is clean and `document.forms.length > 0` on `/booking/` and `/reviews/`.
4. Booking form: the pet-count chips (1 / 2 / 3+) show and hide the right blocks,
   and `new FormData(form).keys()` contains no fields from a hidden block.
5. At a 375 px viewport: the hamburger appears, opens and closes, and
   `document.documentElement.scrollWidth` does not exceed `window.innerWidth`.
6. Do **not** test-submit the live forms casually — it emails Alejandra. Mock
   `window.fetch` instead.
7. After pushing, cache-bust when checking, since Pages serves with
   `Cache-Control: max-age=600`:

```bash
curl -sI "https://katty-co.github.io/services/?cb=$RANDOM" | head -1
```
